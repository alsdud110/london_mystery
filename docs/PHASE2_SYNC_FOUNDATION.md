> **표기:** `[DONE]` 구현·테스트 완료 · `[PROPOSAL]` 승인 필요 · `[OPEN]` 결정 필요

## 1. 저장 안정성 [DONE]

**확인한 사실:** Android 레거시 SharedPreferences는 키마다 `commit()`(키 단위 원자적·순서 보장), iOS는 `UserDefaults` 키 단위 기록. **여러 키에 걸친 저장은 원자적이지 않음** → 기존 코드는 "Coin 지급 저장 후 미션 해결 저장 전 종료" 같은 부분 저장이 가능했음.

**해결:** `SaveJournal` (`lib/data/sync/save_journal.dart`)
1. 여러 키 저장 시 모든 값을 저널 키 하나(`lm.p.<id>.journal.v1`)에 먼저 기록 (키 하나 = 원자적)
2. 각 키 기록
3. 저널 삭제

다음 시작 시 남은 저널이 있으면 그대로 다시 기록(같은 값 재기록 = 무해) → **전부 또는 전무**. 읽을 수 없는 저널은 기록 전 단계이므로 폐기. 저널은 자기 프로필 네임스페이스 키만 건드릴 수 있음(레거시 원본·기기 키 보호).

**트랜잭션:** `ProgressRepository.transaction(body)` — 동기 블록 안의 모든 저장을 하나의 저널 커밋으로. 적용 지점:

| 동작 | 함께 저장되는 것 |
|---|---|
| 미션 정답 (`submitAnswer`) | Case 진행 + Coin 지급 + Season 해결 + 각 outbox 이벤트 |
| TIP 공개 (`revealTip`, 신규) | Coin 차감/소유 + 힌트 공개 + 이벤트 |
| Case 전환 (`openEpisode`) | 이전 Case 시간 + 대상 Case 이름 + Season |
| 새 모험 시작 (`resetAll`) | 네임스페이스 삭제 + 다음 epoch + 새 Wallet |
| Operator 「CASE NN부터」 | 준비된 Case 저장들 + Season |

**변경 없는 저장은 쓰지 않음**(저장 문자열이 같으면 건너뜀) → 쓰기 감소, 불필요한 이벤트 없음.

**하위 호환:** 저장 포맷 변경 없음. 새 필드(`playtest`, `playtestEpisodeIds`)는 값이 있을 때만 기록. 레거시 원본 미변경.

## 2. Outbox [DONE]

`lib/data/sync/outbox.dart`, 키 `lm.p.<id>.outbox.v1`. **데이터와 같은 저널 커밋으로 기록** → 변경은 있는데 이벤트가 없는(또는 반대) 상태가 생기지 않음.

| 필드 | 내용 |
|---|---|
| `id` | 무작위 고유 ID (ack 대상) |
| `profileId`, `kind` | `caseRun` / `season` / `walletEntry` |
| `subject` | Case ID / `season` / Coin 항목 키 |
| `epoch`, `runId`, `runSeq`, `rev` | 변경 버전 |
| `payload` | Coin 항목만(불변). Case·Season은 전송 시점의 최신 저장을 보냄 |
| `playtest` | Operator 데이터 → 운영 업로드 금지 |
| `state`, `attempts` | `pending` / `inFlight`, 전송 시도 횟수 |

**규칙**
- ack 전에는 삭제하지 않음. 알 수 없는/중복 ack는 무시(멱등).
- Case·Season: 같은 대상의 **대기 중** 이벤트는 최신 것으로 대체(최신 상태가 병합에서 항상 이김: 같은 회차는 더 높은 rev, 다른 회차는 더 높은 runSeq). 이미 전송 중(`inFlight`)인 것은 ack까지 유지.
- Coin 항목: 키당 한 번만 대기(재저장해도 중복 없음).
- 앱 재시작 시 `inFlight` → `pending`(재전송; 서버는 중복 무시).
- 실제 전송 없음. 전송기는 `claim` → 전송 → `ack` / 실패 시 `release` 사용(Phase 4).
- 게스트도 기록(대상별 1개로 제한되어 크기 한정). 업로드 여부는 정책에서 차단(§5).

## 3. Case 병합 [DONE] — `mergeCase` (순수 함수)

| 순서 | 조건 | 결과 |
|---|---|---|
| 1 | epoch 다름 | 높은 epoch 승. 진행이 있는 쪽이 지면 `preserved`로 반환(보존) |
| 2 | `runSeq` 다름 | 높은 회차 승 — **Play Again 이전 회차 부활 없음**, 보존 안 함(의도된 재시작) |
| 3 | 같은 `runId` | 결합: 완료·증거·단어·배지 합집합, 시도·오답·힌트 최댓값, 최초 시작·해결 시각, 플레이 시간 최댓값, XP 규칙은 양쪽 기록 유지(같은 미션은 로컬 우선) |
| 4 | 같은 `runSeq`, 다른 회차 | 한쪽이 빈 회차면 다른 쪽 채택. 아니면 **충돌**: 완료 수 → rev → 플레이 시간 → 로컬 순으로 진행 쪽 선택, 다른 회차는 `preserved`로 보존 |
| — | `runId` 없는 레거시 두 개가 다름 | 같은 회차로 단정하지 않고 충돌로 보존 |

멱등: `merge(merge(a,b), b) == merge(a,b)`, `merge(x,x) == x` (테스트로 확인).

**Season:** 해결 기록 합집합, 활성 Case는 기기 고유 선택(로컬 우선). Operator 해결 표시는 해결한 모든 쪽이 Operator일 때만 유지.

**reset epoch:** 「새 모험 시작」마다 프로필 네임스페이스의 `meta.v1` epoch +1(초기화와 같은 저널 커밋). 이후 모든 저장·이벤트는 새 epoch → 다른 기기의 이전 데이터가 초기화를 되돌리지 못함.

## 4. Wallet 병합 [DONE] — `mergeWallet`

- 키 기준 합집합. 같은 키·같은 금액 = 한 항목(지급 1회).
- **같은 키·다른 금액 = 충돌**: 로컬 항목 그대로 유지, 잔액 변경 없음, 충돌 기록 보존(`lm.p.<id>.conflicts.v1`). TIP 소유는 키가 있으므로 유지.
- 보정 지급·잔액 조정 없음. 병합 결과가 음수여도 그대로 둠(정책은 §6에서 승인 후).
- XP V3/V4: Case 회차의 `xpRules`로 보존(Wallet과 무관).

**적용기(`SyncApplier`, 미연결):** 다른 사본의 데이터를 위 규칙으로 적용. 같은 데이터 재적용 시 변화 없음, 충돌은 1회만 보존, 상대에게서 받은 것은 다시 보내지 않고 결합 결과만 대기열에 넣음. 다른 기기의 초기화(더 높은 epoch)를 받으면 로컬 저장 전체를 충돌로 보존한 뒤 이동.

## 5. Operator 데이터 [DONE]

**기존(Phase 1) 한계:** 프로필 전체를 `playtest`로 표시 → 정상 진행까지 영구 동기화 불가, 반대로 표시 전 데이터와 구분 불가.

**변경 — 기록 단위 출처**

| 기록 | 표시 시점 |
|---|---|
| Case 회차 `GameProgress.playtest` | 일반 규칙상 잠긴 Case(Operator로만 열림)에서 진행이 생길 때, 또는 「CASE NN부터」가 만든 회차 |
| Season `playtestEpisodeIds` | 위 회차의 Final 해결, 「CASE NN부터」가 해결 처리한 Case. 이후 정상 해결 시 해제 |
| `CoinEntry.playtest` | 위 Case에서의 미션 보상·TIP |

"일반 규칙상 잠김"은 Operator로 해결된 Case를 해결로 치지 않고 판정(`openedOnlyByOperator`) → 「CASE NN부터」 이후 열린 Case의 플레이도 Operator 데이터.

**업로드 차단(`SyncPolicy`)**
- Operator 도구가 있는 빌드(debug, `LM_PLAYTEST`) → 운영 클라우드 사용 불가.
- 게스트, `needsReview` 프로필 → 업로드 없음.
- **Phase 1에서 `origin: playtest`로 표시된 기존 프로필 → 기록을 구분할 근거가 없으므로 전부 업로드 금지 유지(정상 기록으로 바꾸지 않음).**
- 그 외 프로필은 `playtest` 기록만 제외하고 정상 기록은 업로드.

## 6. 음수 Coin 잔액 정책 — 비교 [PROPOSAL]

상황: 잔액 20에서 두 기기가 오프라인으로 서로 다른 TIP 2(각 −20)를 구매 → 병합 잔액 −20. 현재 구현은 **아무것도 보정하지 않고 그대로 둠**(테스트로 고정).

| 대안 | 동작 | 장점 | 위험·비용 |
|---|---|---|---|
| A. 부채 허용 | 장부는 −20 그대로, 화면은 `max(0, 잔액)`. 가격 판단도 0 하한 → 부채 중 TIP 2는 기존 「무료 도움」. 다음 보상이 부채부터 상환 | 장부 진실성, Coin 생성 없음, 기존 규칙과 자연스럽게 맞음, 서버 로직 불필요 | "+30 COINS" 후 잔액이 30보다 적게 오를 수 있음 → 아이 혼란 가능, 표시 문구 필요 |
| B. 구매 시 온라인 검증 | 유료 TIP은 서버 확인 후 차감 | 음수 원천 차단, 정확 | 오프라인에서 TIP 2 구매 불가 → 오프라인 경험·GET A TIP 규칙 변경, 서버 함수(비용) 필요 |
| C. 오프라인 TIP 구매 제한 | 오프라인에선 TIP 2를 무료 도움으로만 | 단순, 음수 없음 | 오프라인에서 경제 규칙이 달라짐, 비행기 모드로 무료 획득 가능 |
| D. 충돌 시 보정 | 병합 후 0까지 채우는 `reconcile` 항목 | 단순 | 근거 없는 Coin 생성, 반복 악용 가능 — **지침상 채택 불가** |
| E. 서버 순서 확정 | 서버가 도착 순서로 처리, 잔액 부족 구매를 무료 도움(0)으로 확정해 같은 키 금액을 갱신 | 음수 없음, 공정 | Cloud Functions 필요, 로컬 항목 금액이 사후 변경됨(현재 "같은 키 다른 금액=충돌" 규칙과 별도 처리 필요) |
| F. 기기별 오프라인 예산 | 오프라인 구매를 기기별 예약분 안에서만 | 음수 없음 | 복잡, 아이에게 설명 불가 |

**권장:** MVP는 **A(부채 허용 + 0 하한 표시)**. Coin이 결제·광고 등 현금 가치와 연결되는 시점에 **E**로 이행. 구현은 승인 후(표시·가격 판단 변경은 GET A TIP 화면 동작에 영향 → UI 검토 필요).

## 7. installId와 프로필 복구 [DONE]

- `lm.device.v1` `{schema, installId, createdAt}` — 첫 시작에 무작위 생성, 재시작해도 유지, 앱 삭제 시 사라짐. **인증·권한·비밀값으로 사용 금지**(누구나 읽고 복사 가능). 게스트 → 계정 연결 시 설치 구분용.
- 프로필 목록 손상 시: 발견된 네임스페이스를 **모두 목록에 등록(삭제·누락 없음)**.
  - 이전 기록 표식이 가리키는 프로필이 있으면 그 프로필로 플레이, 나머지는 `needsReview`.
  - 표식 없이 여러 개면 **키 개수가 아니라 저장된 마지막 활동 시각** 기준으로 플레이를 이어가되, **모든 후보를 `needsReview`로 표시해 보호자 확인 전 동기화 차단**.
